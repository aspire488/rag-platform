## 1. Motivation

Two owner-driven facts make the local-first *generation* path the wrong default for this machine, while leaving the local-first *retrieval* core untouched:

1. **Resource safety (overriding principle).** The owner's binding requirement is that system resource safety outranks all features and benchmarks: a useful, measurable RAG engine that runs comfortably on this 15 GB laptop — not maximum features. Incident evidence recorded in `docs\RESOURCE_BUDGET.md` §5.5 (2026-10-19; classified there as incident evidence, **not** valid BG-1a results — no throughput data) showed an 8B-class local model driving host RAM to an emergency abort (RAM floor observed at 148 MB) with the start gate repeatedly failing at idle. Cloud inference, when explicitly enabled, removes that local RAM pressure entirely.
2. **Architecture request.** The owner directed this revision: cloud-first generation (Groq → Gemini → OpenRouter as candidates) with Ollama retained only as a guarded, resource-gated local fallback, while ingestion, chunking, keyword/vector search, ranking, authorization, evidence assembly, citation mapping, evaluation, and observability stay local and fully functional when every LLM provider is unavailable.

Crucially, "cloud-first" is documented as the **configured failover order**, not the default state: egress stays off, no provider is configured or authenticated, retrieval-only remains the default mode, and every existing resource gate, threshold, and approval gate remains binding (§2 Z3/Z4/Z10/Z14).

## 10. Addendum — Phase 4 owner decision entry (2026-10-20, accepted implementation decisions)

**Date:** 2026-10-20
**Scope:** Documentation-only addendum recording four owner decisions accepted at Phase 4 closure. Sections 1–9 above are the original 2026-10-19 change note and are preserved unchanged. This entry revises no plan section, relaxes no gate or threshold, and creates no §14 D-number — D13–D18 remain pending. Phase 4 passed its second independent read-only acceptance review on 2026-10-20 (verdict **ACCEPT**; the reported full suite of 234 passing tests is historical evidence recorded by that review, not re-run here).

**1. Input file-size cap — 50 MiB hard maximum (accepted).** The per-file ingest cap is **50 MiB = 52,428,800 bytes**, inherited from the earlier plan's v1 §6.2 "Ingest file size" row (the same bounds table whose chunk row v2.4 §10.2 carried forward). It is implemented as `Settings.max_input_file_bytes` (default and `le` both 50 MiB — un-raisable above the cap). Enforcement is two-stage: a pre-read `stat` check rejects oversized files **before any read**, and a post-read re-check against the bytes actually read **detects** a file that grew between `stat` and read and **rejects** it before decoding or PDF parsing. The post-read check does **not** prevent the transient allocation — only a same-handle bounded read could — and it is documented as detection, not prevention, in `ingestion\loaders.py` (module docstring and inline comment); the two stale "before any read" code phrases found by the second review (`ingestion\errors.py` `FileTooLargeError` docstring, `config.py` size-cap comment) were corrected in the same authorized cleanup.

**2. Declared-date convention (accepted).** A declared date is recognized **only** as a line shaped `date: YYYY-MM-DD` (case-insensitive, leading whitespace tolerated) inside the document's *leading block*, defined as the **first 20 non-empty lines**. The value must be a **real calendar date** (ISO `YYYY-MM-DD` that exists on the calendar; no fuzzy parsing, no locale guessing). Outcomes are recorded explicitly with the four statuses **`ok` / `missing` / `malformed` / `ambiguous`**; ambiguous declarations store no value and are never auto-resolved, and repeated identical declarations count as one. A declared date is **never inferred from filesystem metadata** (mtime is recorded separately as `source_mtime`).

**3. Timestamp semantics — three distinct fields (accepted interpretation of v2.4 §4.1).** Metadata carries **`declared_date`** (the author-declared calendar date above), **`ingested_at`** (the injected/current ingestion clock, ISO-8601 UTC — injectable for deterministic tests), and **`source_mtime`** (filesystem metadata, ISO-8601 UTC). This resolves the wording tension between §4.1 line 182 ("file mtime recorded at ingest as `ingested_at`") and line 184 (`declared_date` vs `ingested_at` labeled distinctly): **line 184's distinction governs**, line 182's literal wording is superseded, and mtime is preserved as its own field rather than conflated into the ingestion clock or discarded.

**4. PDF citation offsets (accepted).** Chunk citation ranges are **Unicode code-point offsets into the extracted text** (Python `str` indices; SQLite `length()` counts code points too, so schema checks and chunker agree). For PDFs, extracted text is a **lossy page-text reconstruction** (per-page text joined with a blank line, whitespace-only pages dropped) and therefore **does not promise direct PDF byte, page, or visual-layout coordinates** — only positions within the extracted string. **No page/line mapping table is added in this phase**; whether Phase 9 citation requirements need one is a future owner decision, taken then.

**Design decisions recorded:**
1. **One orchestration, two surfaces.** API and CLI both call `api.run_query` (existing Phase 5 `HybridRetriever` + Phase 6 `answer_query`); neither re-implements retrieval, abstention, or citation logic. The API/CLI retriever is **lexical-only** (`embedder=None, store=None`): the dense leg stays gated behind the BG-1a/D3 verdict, and an AST import-scan test asserts the Phase 7 modules never import `sentence_transformers`, `qdrant_client`, `torch`, or the embeddings/vectorstore packages.
2. **Error mapping.** One envelope `{"error": {"category", "detail"}}` with constant sanitized details: `413 request_too_large` (content-length bound before parsing), `422 invalid_request` (malformed/empty/extra-field/over-cap; input values never echoed), `503 storage_unavailable`, `500 internal_error` (exception class name logged only, never messages or tracebacks). Generation-unavailable, invalid-citation, and abstention outcomes remain truthful **HTTP 200** retrieval-only responses — never converted to 500s.
3. **Tracing on existing contracts.** `traces` + three `trace_stages` rows (`retrieval`, `generation`, `response`) per completed query, against the Phase 2 schema unchanged (no migration). Content rule: digests, enums, counts, timings, provider/model labels only — never queries, prompts, retrieved text, paths, keys, or exception details; `excerpt` always NULL and `trace_authz` empty until M2; `cache_status="not_implemented"` until M4. **Failure policy (tested):** trace persistence is best-effort — a failed write is logged (class name) and the response returns unchanged; it neither fabricates success nor turns a valid answer into an error. Rejected (4xx) and storage-failed requests are not traced; full nine-stage completeness belongs to the Phase 8/M3 recorder.
4. **CLI contract.** `query` prints a bounded summary by default (no passage-content dump) with `--json` for the full canonical response; exit codes `0` (any canonical outcome incl. retrieval-only), `2` (invalid input), `3` (storage/internal failure). `report` renders raw recorded traces only — attribution analytics are not faked. Documented in README §12.2.
5. **TestClient portal caveat (recorded for future sessions).** starlette's `TestClient` starts its asyncio event loop per request when used outside a `with` block, and on Windows that creates a loopback `socketpair()` self-pipe connect belonging to the *test harness*. The Phase 7 socket-guard tests therefore enter the `with TestClient(...)` context before installing the guard, so the guarded region covers the actual `/health`+`/query` handling with **zero** socket operations of any kind.
